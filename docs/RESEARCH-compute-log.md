> 하드웨어: 2×H100 80GB(공용, A2A 운영 스코어러가 약 3.8GB 상주) · 서빙 Apple M5 16GB.

vLLM 엔진 초기화는 **회당 33~35초**(32B tp=2 기준, torch.compile 캐시 적중 시). 짧은 작업일수록
이 고정비 비중이 크다 — 판정 v2는 초기화가 실행 시간의 절반에 가깝다.

## 3. 평가가 진짜 병목이었다

| 방식 | 구조 | 실측 |
|---|---|---|
| HF `generate()` | 체크포인트마다 모델 재로딩 + **케이스별 1건씩** 생성 | RL 20체크포인트에 **약 1시간** |
| vLLM LoRA 핫스왑 | 베이스 1회 로딩 + 어댑터 교체 + **전 케이스 배치** | 미측정(도입 예정) |

HF 판이 느린 이유는 두 가지다. (1) 체크포인트마다 2.4GB 가중치를 다시 올린다.
(2) `generate()`를 케이스마다 호출해 배치를 전혀 안 쓴다.

`Exaone4ForCausalLM`은 vLLM LoRA를 지원하고(`packed_modules_mapping` 확인), 이 버전에서
`enable_lora`는 `LLM(**kwargs)`로 전달된다. 베이스를 한 번만 올리고 `LoRARequest`로 어댑터를
갈아끼우면 (1)이 사라지고, 프롬프트를 한 번에 던지면 (2)가 사라진다.

**두 구현을 모두 유지한다.** vLLM 판은 빠르지만 의존성이 무겁다. 공개한 어댑터를 제3자가
검증할 때는 transformers만 있으면 되는 HF 판이 낫다. 두 경로가 같은 수치를 내는지 대조하는
것도 구현 오류 점검이 된다.

## 4. 병렬화 여지

| 방법 | 근거 | 기대 |
|---|---|---|
| 두 학습을 GPU0/GPU1 동시 | 1.2B 학습이 약 40GB — 두 판이 한 장씩 들어간다 | 벽시계 절반 |
| 학습(GPU0) + 판정(GPU1) 병행 | 실제로 적용해 A2 학습 중 C 판정을 붙였다 | 22분 → 13분 |
| 32B tp=1로 단일 GPU | 판정 v1을 tp=1로 돌려 72초 | 남는 GPU 확보 |

**주의(실제 사고):** `gpu_memory_utilization=0.92`로 잡았다가 GPU0에 상주하는 A2A 운영
스코어러(3.78GB)와 부딪혀 OOM으로 죽었다. 공용 장비에서는 0.85 이하로 두고, 시작 전
`nvidia-smi`로 여유를 확인해야 한다. 또 `pkill`이 vLLM 엔진 자식 프로세스를 못 죽여
**70GB를 점유한 고아 프로세스**가 남아 다음 실행을 막은 적이 있다 — PID를 직접 확인해
`kill -9` 해야 한다.

## 5. 실제로 시간을 먹은 것 — GPU가 아니었다

세션 전체에서 GPU 실사용은 **1~2시간**이고 나머지는 코드 작성·분석·재작업이었다.
재작업의 원인:

| 사고 | 손실 | 원인 |
|---|---|---|
| 학습 시퀀스 절단 | 학습 1판 폐기(479s) + 평가 시간 | `max_seq_len` 미검증 — 12/160건이 잘려 EOS 없는 타깃 학습 |
| 학습·서빙 분포 불일치 | 학습 1판 폐기(386s) + 평가 | 학습은 해석된 텍스트, 서빙은 번호 |
| 스키마 미강제 | 비교 1판 폐기(220s + 분석) | vLLM만 강제하고 Gemini는 프롬프트로만 |
| trl API 변경 | RL 4회 재시작 | `max_prompt_length` 제거됨 |
| NCCL 표기 불일치 | RL 1회 재시작 | server 모드 → colocate로 우회 |
| GPU 고아·OOM | 2회 재시작 | 위 §4 |
| Gemini 스키마 폭주 | 스모크 1회 | `propertyOrdering` 미지정 |

**결론: 이 규모에서는 GPU 병렬화보다 실행 전 검증이 총 소요를 더 줄인다.** 그래서
`train_chat_sft.py`에 학습 전 데이터 검문(절단·빈 답변)을 넣어 통과 못 하면 시작하지
않게 했고, 학습 코드를 독립 에이전트에게 감사시킨 뒤 실행하는 절차를 도입했다.

## 7. 로컬 서빙 (Apple M5)

MLX Q8 변환은 성공했으나 **처리량은 측정하지 못했다.** 측정 시점 머신이 스왑
9.2/10GB를 쓰는 상태여서 9~15 tok/s가 나왔는데, 같은 시점 MLX 원시 행렬곱은 28 TFLOPS로
정상이었다. 즉 이 수치는 MLX 성능이 아니라 그 시점 메모리 압박을 잰 것이라 무효다.
재측정은 메모리를 비운 뒤 해야 한다.

| 항목 | 값 |
|---|---|
| 변환 | EXAONE 1.2B → MLX Q8, 1.3~1.4GB, 8.5~9.0 bits/weight |
| RL 재작성기 응답 | 1~3초/질의 (같은 메모리 압박 상태에서 측정) |

## 8. 재현 시 참고

- transformers 5.x는 `rope_theta`/`rope_scaling`을 `rope_parameters` 하나로 합쳐 저장한다.
  mlx-lm은 분리 형식을 요구하므로 변환 전 되돌려야 한다(`fix_config_for_mlx.py`).
- trl 1.9.1은 vLLM 0.17~0.25.1만 지원한다. 추출 파이프라인이 쓰는 vllm 0.26과 충돌하므로
  RL 전용 conda 환경을 따로 만들었다.
- `.gitignore`는 줄 끝 주석을 지원하지 않는다. 패턴 뒤에 주석을 붙이면 공백까지 포함한
  전체가 패턴이 되어 아무것도 무시되지 않는다.
